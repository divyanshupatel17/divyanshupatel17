# How this profile is built

The README on this account is not written. It is compiled.

`profile.config.json`, live GitHub data, and a build-time probe of each shipped
product go in. Five custom SVG panels in two themes, plus a generated
`README.md`, come out. A workflow rebuilds it daily.

```
profile.config.json ─┐
GitHub REST/GraphQL ─┼─► core/github.py ─► data.json ─┐
production HTTP probe┘                                ├─► panels/*.py ─► assets/*.svg
avatar ─► core/portrait.py ─► portrait.json ──────────┘
                                    README.template.md ─► README.md
```

## Identity: PHOSPHOR

A warm amber terminal on near-black. Chosen deliberately: essentially every
developer profile on GitHub is cyan-on-navy or green-on-black, and amber is
both instantly recognisable and almost unused. It also survives GitHub's image
proxy better than saturated cyan, which fringes when downscaled.

**Colour.** One accent, one ember for secondary emphasis, one green reserved
for live state, and a neutral ink ramp. Series colours are generated by
stepping the accent toward muted rather than by picking new hues. The five-stop
`glow` ramp is the phosphor decay curve, used for the portrait dots and the
skyline tower tops so both read as the same material.

**Type.** A terminal is a monospace object, so mono carries the page. The sans
stack appears only where a number needs headline weight. Both resolve inside
GitHub's proxy without webfonts. Column positions are computed from a known
mono advance width, which is how the dotted leaders line up without measuring
text at runtime.

**Motion.** Motion resolves. Entrances settle within about three seconds and
freeze. Exactly three things animate forever, and each encodes state rather
than decoration: the live status pulse, the terminal caret, and the mascot's
wingbeat.

Every token lives in [`generator/core/tokens.py`](../generator/core/tokens.py).
Change the accent there and both themes, every series colour, the skyline, the
portrait, the shields wall, the snake and the trophies all follow, because
`WIDGET` in the same file is what the third-party widget URLs are built from.

## Panels

| Panel | Shows | Source |
| :-- | :-- | :-- |
| `hero` | Halftone portrait and a manifest of role, origin, stack and contact | avatar + config + live |
| `production` | Shipped products, each with a real HTTP status and response time | build-time probe |
| `pulse` | Streaks, contributions, repos, stars, weekday cadence, 12-month volume, language split | live |
| `skyline` | 364 days of contributions extruded into towers | live |
| `mascot` | Relay, a pixel moth orbiting the lamp | drawn |

Each is a module under `generator/panels/` exporting `render(data, theme)`.
Adding one means adding a file, a line in `PANELS`, and a `<picture>` block.

### The portrait

The hard part is not the halftone, it is the photograph: a GitHub avatar is
usually a backlit phone snap against a busy background, which is the worst case
for a naive tone map — the sky comes out denser than the face. Three things fix
it, in order.

1. **Local contrast, not global tone.** Each cell is compared against a blurred
   copy of its own neighbourhood, so a pixel is inked for being darker *than
   its surroundings*. Backlight gradients cancel; smooth areas like open sky
   produce no ink at all because they match their own blur.
2. **A chroma key on blue**, for whatever sky survives step one.
3. **An elliptical spotlight and a floor fade**, so shoulders and scenery
   dissolve instead of ending on a hard edge.

The result is trimmed to the bounding box of lit cells so the subject fills its
frame, then cached to `assets/portrait.json`. The expensive step runs once; a
normal build needs neither Pillow nor the network.

Swapping the photo means changing `portrait.source` and re-running with
`--photo`. If the new photo is lit differently, `crop`, `centre`, `spot`,
`gain` and `floor` are the five dials.

### The skyline

The 3D contribution graph everyone links to is a third-party action rendering
in someone else's palette. This draws the same idea from the same data in
system colours.

The projection is dimetric, not the usual 45° isometric: a true isometric view
of 52×7 produces a thin diagonal ribbon that wastes most of a 1200px canvas.
Tilting the week axis nearly flat and steepening the weekday axis lays the year
out as a wide city block. The two basis vectors `U` and `V` are the only thing
controlling it.

Towers are drawn back to front, so the painter's algorithm handles occlusion
with no z-sorting. Heights are continuous; colours snap to the five phosphor
stops, so brightness reads as a band rather than an arbitrary interpolation.

## Honesty rules

These are the constraints that matter most, and they are enforced rather than
intended.

- **Nothing measurable is typed by hand.** Repo counts, stars, streaks,
  languages, location, account age and contribution history all come from the
  API. The config holds only what an API cannot know: role, education,
  curated tool lists, and copy.
- **Product status is probed, not claimed.** Each production card carries the
  HTTP status and response time measured against the live origin at build time.
  If a product is down when the workflow runs, the card says so.
- **Estimates are labelled as estimates.** With a token, the language split is
  real per-repository byte counts. Without one, that would exhaust the
  unauthenticated hourly quota, so the build falls back to attributing each
  repo's size to its primary language *and the panel says which measurement it
  is showing.*

## Guardrails

`generator/check.py` fails the build on any of five things, because these are
the five ways a generated design system rots:

1. **Config sanity** — copy length limits derived from real render geometry, so
   an over-long line fails in CI instead of wrapping badly on the page.
2. **Contrast** — every text token clears WCAG AA against both surfaces in both
   themes, asserted rather than assumed.
3. **Well-formedness** — a malformed SVG renders as a broken image and GitHub
   gives you no error to read.
4. **Weight** — 130 KB per asset, 320 KB per theme. Currently ~185 KB per theme.
5. **Palette** — every colour in every asset must be a token or a blend of two
   tokens. This one has already caught a real drift: the skyline's tower tops
   were three-way mixes, which is what prompted quantising them to the ramp.

## Third-party widgets

Four things on the page are not generated here. Each is themed from `WIDGET`
so it renders inside the palette rather than punching a hole in it.

| Widget | Why it is not generated | Theming |
| :-- | :-- | :-- |
| Contribution snake | It animates rather than summarises, which is something the panels do not do | palette passed to the action |
| Shields wall | The icon set is the point, and simple-icons is not worth reimplementing | each badge wrapped in a `<picture>` with dark and light sources |
| Trophies | Scoring is the third party's, and rebuilding it would just be copying | colours via query params |
| Visitor counter | Requires server-side state a static repository cannot hold | colour via query param |

## Setup

Python 3.10+. **No dependencies** for a normal build; Pillow only for
re-dithering the portrait.

```bash
python -m generator.build --fetch          # real data, works without a token
python -m generator.build --fetch --photo  # also re-dither the portrait
python generator/check.py
open generator/preview.html                # both themes at GitHub's real width
```

The data layer works with or without a token. A token adds private
contribution counts and exact language bytes; without one it uses REST plus
the public contributions endpoint. That tokenless path is why CI can verify a
change against real data with no secrets, and why there is no fixture file.

Add a classic PAT as the repository secret `GH_TOKEN` (scopes `read:user`,
`repo`) if you want private contributions counted. The daily workflow otherwise
runs on the built-in `GITHUB_TOKEN`.

| Workflow | Trigger | Does |
| :-- | :-- | :-- |
| `profile.yml` | daily 03:17 UTC · config push · manual | fetch, probe, render, check, commit if changed |
| `snake.yml` | daily 03:41 UTC · manual | regenerate the snake onto the `output` branch |
| `verify.yml` | pull request · non-main push | render and check with no secrets |

**Never edit `README.md`.** It is generated from `README.template.md` and
overwritten on every build.
